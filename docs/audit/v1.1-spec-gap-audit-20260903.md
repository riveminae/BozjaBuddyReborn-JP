# BozjaBuddyReborn-JP v1.1 requirements gap audit

Date: 2026-09-03
Branch: `feat/bocchi-navigation`

This audit is intentionally requirements-first. `docs/implementation/...progress.md` is not accepted as proof that behavior is correct.

Normative precedence:

1. `docs/requirements/BozjaBuddyReborn-JP_v1.1.0.md`
2. `docs/design/BozjaBuddyReborn-JP_v1.1.0_detailed-design.md`
3. `docs/implementation/BozjaBuddyReborn-JP_v1.1.0_execution-plan.md`
4. current implementation/progress

## Confirmed hard divergences

### GAP-01: top-level settings categories do not match the approved UI design

Approved categories:

- 周回
- 生存
- ロストアクション
- 移動
- Relic
- 詳細設定

Current `Windows/ConfigWindow.cs` exposes:

- 戦闘
- CE / スカーミッシュ
- 生存
- 移動
- エリア
- ロストアクション

This is not just naming: implementation-focused combat/zone controls dominate the normal UI, while Relic and advanced/debug separation are missing from the approved structure.

Action: reorganize existing controls without changing behavior first. Keep low-level diagnostics, callback logging, BOCCHI cost tuning, legacy escape hatch, etc. under 詳細設定.

### GAP-02: travel aggro exposes a forbidden FightBack behavior

Approved behavior is fixed: if field mobs aggro during travel, keep moving/flee; do not stop to fight. Mounted travel must especially avoid actions that can dismount the player.

Current code still has:

- `TravelAggroResponse.FightBack`
- a UI radio button `停止して反撃する`

Action: remove the user-facing FightBack option from v1.1 normal behavior. Keep any legacy serialized field only if migration compatibility requires it, but normalize v1.1 behavior to KeepRunning.

### GAP-03: required combat dependencies are presented as optional user toggles

Approved unattended runner requires:

- vnavmesh
- Rotation Solver Reborn
- BossMod/BossMod Reborn

`DependencySupervisor` correctly treats all three as required, but `ConfigWindow` still allows the user to disable BossMod avoidance and RSR rotation. This creates a state where required plugins are installed yet BBR deliberately disables the behavior needed for autonomous farming.

Action: normal v1.1 UI should present required dependency status, not allow turning core unattended behavior off. If emergency/diagnostic disable switches are retained, place them in 詳細設定 and make Start/reporting explicitly state that unattended operation is degraded.

### GAP-04: approved per-Lost-Action `持込` / `自動使用` permissions are not exposed correctly

`Configuration` and `SurvivalPolicy` contain:

- `LostActionBringPermissions`
- `LostActionAutoUsePermissions`
- correct Deep Essence default-off semantics

But current UI still primarily edits the old `AutoLostActions` one-dimensional list.

Approved semantics require two independent toggles per action:

- bring OFF + auto-use ON is valid
- bring ON + auto-use OFF is valid

Action: normal survival preset UI must show both columns for survival candidates; 詳細設定 must allow searching/configuring all Lost Actions. Legacy `AutoLostActions` must not be presented as the v1.1 permission model.

### GAP-05: CE registration can be skipped by a user-configurable remaining-time threshold

Approved rule: register immediately when an eligible CE becomes registerable. There is no user preference to ignore a registerable CE because its remaining window is below an arbitrary 15–60 second threshold.

Current code exposes `MinRegisterSecondsLeft` and lets the UI set it between 10 and 60 seconds. `TargetSelector.IsEligible` rejects the CE when below that value.

Action: retain only the actual protocol/game safety floor if needed (for example the known under-10-second refusal), not a general user preference capable of violating immediate registration.

### GAP-06: remote CE eligibility still requires a position for a reason that belongs to old travel-to-CE behavior

Current `TargetSelector.IsEligible` rejects `!ce.HasPosition` with a comment that the CE cannot be routed to without a position.

Approved v1.1 CE registration is remote and does not travel to the CE marker to register.

Action: separate registration eligibility from geographic metadata. Position/region may still be needed for Relic drop classification, but lack of a route position must not independently block a remotely registerable CE.

### GAP-07: progress marked UI category work DONE while approved category layout is not implemented

`docs/implementation/BozjaBuddyReborn-JP_v1.1.0_progress.md` marks `P11-01` DONE, but GAP-01 shows the approved top-level structure is absent.

Action: downgrade P11-01 until the approved structure is actually implemented. `DONE` means spec-complete, not merely "tabs exist".

## Major incomplete items that are not safe to fake

### GAP-08: Start-one-click Initialize flow is not complete

Approved flow requires Start to determine whether Initialize is needed, navigate to Cache when needed, build/verify the survival loadout, and only then farm.

Current `BozjaController.Start()` enters Running without an `InitializationCoordinator`/transaction phase.

This is partially blocked by the unresolved Cache↔Holster server-backed transfer mechanism. That blocker is valid; guessed callbacks or direct memory writes are forbidden.

Action: keep the transfer effect BLOCKED, but do not describe Start/Initialize as completed. Implement every safe preflight/state boundary around the transfer separately where possible.

### GAP-09: Cache↔Holster transfer remains a real blocker

Current research correctly concludes that public ClientStructs expose inventory state but not a proven server-backed transfer function/callback.

Action: do not guess. Continue using the callback probe/research path and keep Initialize/refill effect incomplete until evidence exists.

## Potentially misleading implementation artifacts to clean up

- `BozjaController` XML comments still describe old "travel to an engagement and walk in" behavior although implementation now registers CEs remotely. Comments used by AI contributors must reflect the current specification.
- `Configuration.DangerousEnemyMinLevel` retains old level-based language even though v1.1 danger selection is I/II/III vs IV/V/★. If kept only for migration, document it as dead compatibility state and ensure no runtime/UI path relies on it.
- Generic `StickyObjective` controls should not be allowed to override explicit Relic target transitions, CE selection, completion/100%/expiry abandonment, blacklist, or supply safety rules.

## Corrective implementation order

1. Fix GAP-02 travel aggro behavior and remove normal FightBack UI.
2. Fix GAP-05/GAP-06 remote CE eligibility so registration follows the approved rule.
3. Fix GAP-04 dual Lost Action permission UI.
4. Fix GAP-01 UI category structure and GAP-03 dependency controls placement.
5. Downgrade/correct progress statuses that were marked DONE prematurely.
6. Clean stale comments/compatibility fields that can mislead future Codex runs.
7. Continue safe parts of Initialize, while leaving only the proven transfer effect BLOCKED.

Every corrective commit must cite the requirement it restores, update static contracts where useful, and pass Debug/Release/test workflow before being called complete.
